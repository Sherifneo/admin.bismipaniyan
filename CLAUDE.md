# Bismi Bakery Admin Portal — Project Context

React 19 + Vite admin/back-office UI for Bismi Bakery, at `admin.trpbismipaniyan.com`. Read this before making changes.

## What this is

The internal staff-facing tool for **Bismi Bakery & Paniyan Shop**, a traditional bakery manufacturer in Karaikal, Puducherry. Not a customer-facing app — no shopping cart, no checkout, staff-only login. See `BUSINESS-MODEL-FEATURES.md` for the business context.

One of three sibling repos for the same business:
- `Bismipaniyan` — the public website (`trpbismipaniyan.com`)
- **`admin.bismipaniyan`** — this repo (`admin.trpbismipaniyan.com`)
- `api.bismipaniyan` — the backend API (`api.trpbismipaniyan.com`)

Separate repos, separate Hostinger deploy targets — see `DEPLOYMENT.md`.

## Architecture

Deliberately follows a proven shell pattern (originally from a sibling project, nammahearth) — reuse the generic parts verbatim, design business modules fresh per this client's actual operations:

- **`src/auth/`** — token-in-localStorage auth (`bp_admin_token`), `AuthContext` boots by calling `/api/admin/auth/me`, `ProtectedRoute` gates by sign-in state, `ownerOnly`, or `requiredPermission`.
- **`src/api/client.js`** — fetch wrapper; a 401 clears the token and fires a `bp-admin-auth-change` event the auth context listens for.
- **`src/api/admin.js`** — one function per backend endpoint, grouped by module (`cashbookApi`, `inventoryApi`, `partnersApi`, etc.).
- **`src/layout/navConfig.js`** — the single source of truth for the sidebar. `App.jsx` generates routes from this same list, so a route can never exist without a nav entry or vice versa. A nav item with no page built yet renders `ComingSoon` automatically. `NAV_ITEMS` is a **tree**, not a flat list (see "Sidebar: Main Module → Submodule" below) — a top-level entry either has its own `path` (a standalone leaf, e.g. Dashboard/WhatsApp Orders/Partners & Shops) or `children` (a collapsible module, e.g. Finance/Products). `App.jsx`'s `flattenRoutes()` walks the tree and emits exactly one `<Route>` per **distinct pathname** (deduped, ignoring any `?tab=` query string) — several children of one module can point at the same page with different `?tab=` values (e.g. Products' UOM/BOM/Change Management children are all `/products?tab=...`) and correctly share one route, never one route per tab. `BUILT_PAGES` is keyed by whichever child ends up "first" for that pathname during flattening — for a module whose first child's key differs from the module's own identity (HR's first child is `employees`, Settings' is `companydetails`), `BUILT_PAGES` needs a matching alias entry (`employees: HRPage`, `companydetails: SettingsPage`) or that route silently falls back to `ComingSoon` — a real bug caught during this rework, worth remembering if a module's child order ever changes.

## Sidebar: Main Module → Submodule (with pin/expand)

The sidebar (`src/layout/Sidebar.jsx`) renders `NAV_ITEMS` as collapsible **Main Module → Submodule** groups instead of a flat list. A module's visibility follows the exact same `ownerOnly`/`requiredPermission` rules as before, just evaluated per-child — a module shows up if at least one of its children passes; its `children` array is filtered down to only the passing ones before rendering. No new permission concept was introduced.

- **Auto-expand**: a module is force-expanded whenever the current URL's pathname matches one of its children (computed fresh every render, not persisted) — plus whatever's manually expanded via the chevron, tracked separately in `localStorage` (`sidebarState.js`, `bp_admin_sidebar_expanded`).
- **Arrow vs. label**: the chevron button only toggles expand/collapse (`stopPropagation`-free, but structurally separate from the link so it never navigates); the module label is a real `NavLink` to that module's first child's path (its "default" page).
- **Active state**: a module header gets `.is-active` if any child's pathname matches the current URL; each individual submenu link gets its own `.is-active` via `isChildActive()` — for a `?tab=`-backed child this compares the FULL pathname+search against that child's own path, so only the actually-open tab lights up, not every tab of that page.
- **Pin**: module-level only (never a leaf/submodule) — `sidebarState.js`'s `bp_admin_sidebar_pinned` (localStorage, per-browser). A pinned module renders once in a "Pinned" section above "All Modules" AND still in its normal position below — never moved, just also shown at the top. This **replaces** the old favorite-star/drag-reorder customization feature entirely (`sidebarPrefs.js` and Settings' "Sidebar" tab were both deleted) — the two systems didn't compose cleanly once items became grouped into modules with sub-items.
- **Tab pages are also sidebar submodules**: every page that has its own internal `TABS` array (Products, Cash Book, HR, Reports, Bank Accounts, Financial Control, Inventory, Settings) now treats **the URL as the source of truth** for which tab is showing — each of these pages was converted from `const [tab, setTab] = useState("defaultKey")` to reading `tab` straight from `useSearchParams()` and writing to it (`{ replace: true }`, no extra browser-history entries) instead of local state. This means a sidebar submodule link like `/products?tab=uom` opens directly on that tab, AND clicking an in-page tab button updates the URL to match — the two can never drift apart in either direction. `useUrlSearch()` (`q`/`from`/`to`) was left untouched; tab state doesn't go through it.
- **Financial Year** (new, `src/pages/calendar/CalendarPage.jsx`, route `/calendar`) lives as a submodule inside Finance — sidebar label is "Financial Year" but the route/file/internal naming stays "Calendar". Pure read-only reference screen: current Indian financial year (1 Apr–31 Mar, `src/utils/financialYear.js`'s `getFinancialYear()`/`listFinancialYears()`) plus a small table of surrounding years. No backend, no API call, not wired into any report — deliberately just a reference utility for now.
- **Mobile drawer**: unchanged structurally from before (`AppShell.jsx`'s `mobileNavOpen` state, `.bp-sidebar-overlay`, `860px` breakpoint) — one fix: the close-on-navigate effect now also depends on `location.search`, not just `location.pathname`, since a `?tab=` submodule link changes only the query string and previously wouldn't have closed the drawer.
- **`src/theme/`** — `theme.css` (CSS custom-property tokens, brand purple `#5b1f97` + amber accent) and `shared.css` (page/table/form/button classes reused by every module).
- **`src/components/`** — Modal, Pagination, SearchBox, StatusBadge, ExportMenu, ReasonConfirmModal — shared across every list page.
- **List-page shape**: search/filter → table → pagination → modal for create/edit → CSV export. Every built module follows this.

## Deploy shape

This is a Vite SPA — `npm run build` produces static files in `dist/`. Hostinger's Node.js App hosting needs a running process, not a bare static host, so `server.js` (a tiny Express static-file server with an SPA fallback) serves the built output. `postinstall` runs `vite build` automatically so a plain `npm install` produces `dist/` before `npm start` needs it. `vite` and `@vitejs/plugin-react` are real `dependencies`, not `devDependencies`, so a production-only install still has what it needs.

## Conventions to follow

- New module: add a nav entry in `navConfig.js` (with `requiredPermission` matching what the backend route expects), a page component in `src/pages/<module>/`, register it in `App.jsx`'s `BUILT_PAGES`.
- Reuse `bp-page-title`, `bp-table`, `bp-btn-primary`/`-outline`/`-sm`, `bp-field-input`, `bp-form-row` etc. from `shared.css` rather than writing new CSS for standard list/form UI.
- No password-reset/change-password screen exists yet — this is a known gap, not an oversight to silently work around.

### "Manage a small list" pattern — tabs on a page, never a nested modal

When a feature needs an owner-editable reference list (categories, positions, statuses, any small admin-managed lookup table used elsewhere as a dropdown), it gets its **own tab on the parent module's page** — not a `Modal` opened from inside another `Modal`. The owner rejected the nested-modal shape explicitly (Cash Book's "Manage categories" and HR's "Manage positions" both started this way and were both corrected to tabs) — a modal-on-modal doesn't have room for a real table and reads as broken/cramped no matter how it's laid out.

Reference: the owner's screenshot pattern is a Dynamics-365-style admin screen — one page, a `bp-tabs`/`bp-tab` bar across the top (Users / Security / Departments / Categories / ...), each tab swapping in a different full-width table+form section on the same page, no page navigation and no popup-inside-popup.

**Shape to follow**, using Cash Book's Categories tab and HR's Positions tab as the templates:
1. The list gets a `TABS` entry alongside the module's other tabs (e.g. `{ key: "categories", label: "Categories" }` next to Cash Book's All/Income/Expense/... tabs) — reuse the page's *existing* tab bar if it has one (Cash Book), or introduce one if it doesn't yet (HR's `HRPage.jsx` wraps `EmployeesList`/`PositionsList`/`SalaryPaymentsList` as tabs, each still its own self-contained component).
2. The list's CRUD UI (add/rename/deactivate/delete, inline edit) becomes a plain `<div>`-wrapped component — not `<Modal>` — so it renders full-width inside the tab instead of a fixed ~420px modal box.
3. Anywhere else in the module that needs to jump to that list (e.g. a "Manage" button next to a dropdown sourced from it) switches the parent's tab state (`onManageX={() => setTab("x")}` threaded down as a prop) instead of opening a nested modal or navigating to a separate route/new tab.
4. If the list benefits from a real code (most master lists do — see Machines/Employees/Vendors), give it one via `nextCode()` the same way, registered in `backend/src/routes/number-sequences.js`'s `TARGET_BY_KEY`.

Do not default to a nested `Modal` for a "manage this list" feature going forward — start with a tab.

## Every new list table needs search — no exceptions

Any new table/list screen (paginated or not) must ship with **both**: `useDataTable` + `ColumnHeader` on every filterable column (client-side precise filtering — starts with/equals/ranges), and `SearchByBar` for a quick "search by [column]" text box. `NumberSequencesPage.jsx` (previously a plain `<table>` with no search at all) was retrofitted with this exact pattern as the reference for "add it to a page that doesn't have it yet" — see its `columns` array and `useDataTable`/`ColumnHeader`/`SearchByBar` wiring. If the list is server-paginated (more than one page can exist), also wire `SearchByBar` to hit the server per the "SearchByBar — server-side per-column search" section above, rather than leaving it client-side-only.

**Every new Number Sequences counter** follows `products`/`boms`/`partner_product`'s pattern exactly: seed the `counters` row via a migration (`INSERT IGNORE INTO counters (counter_key, prefix, current_value, pad_width) VALUES (...)` — never rely on `nextCode()`'s lazy-create-on-first-use alone, since the frontend's `GET /number-sequences/:key/preview` 404s until the row exists, which makes `useCodePreview()` silently fall back to Manual mode instead of showing the live preview), then register it in `backend/src/routes/number-sequences.js`'s `TARGET_BY_KEY` (table/column/pk/label) so it shows up correctly in the Number Sequences screen's **Module** column (added alongside this same change — `GET /number-sequences` now includes `module: TARGET_BY_KEY[counter_key]?.table`, so every sequence row shows which table its codes actually land on).

## SearchByBar — server-side per-column search

`DataTable.jsx`'s `SearchByBar` (the "🔍 ... Search by [column dropdown]" bar above most list tables) used to filter only whatever page of rows was already loaded client-side — so on a paginated list, a match sitting on page 2+ was invisible to it (list page sizes were also bumped 20/25/30 → 100 everywhere around the same time, which alone fixes this for most screens today, but doesn't fix it structurally for a table that ever exceeds 100 rows).

Fixed by giving `SearchByBar` an optional server mode: pass `onServerSearch(columnKey, value)` + controlled `serverColumn`/`serverValue` props and it calls back into the page instead of calling `table.setFilter` — the page owns turning that into a real API call. Without `onServerSearch` it behaves exactly as before (client-side `table.setFilter`), so pages that load their full dataset in one unpaginated call (Employees/Machines/Vendors/StockTransfers/Customers/BankAccounts/Stores/FinancialDimensions/Positions/Team/SalaryPayments) were left alone — there's no "page 2" for search to miss.

Backend side: each wired route's `GET /` gained a `qField` param alongside its existing `q` — a per-route `Q_FIELD_COLUMNS` map picks a single-column `LIKE` when both are present and recognized, falling back to that route's original (often multi-column) `q` behavior otherwise, so the existing top-level `SearchBox` component (which only ever sends bare `q`) is unaffected. Wired so far: **Products** (`product_code`/`sku`/`name`/`uom`), **Partners** (`partner_code`/`name`/`location`), **Production Runs** (`product_code`/`product_name`/`location_name`/`machine_name` — JOIN columns; the `quantity` column is a computed JS string and was skipped), **Cash Book** (`category`/`description` — `q`/`qField` added from scratch, this route had neither before), **Sales Orders** (`so_number` only — also added from scratch; `buyer`/`location_name` skipped since they're unreachable from the route's unjoined COUNT query), **Inventory Transactions** (`trans_id`/`note`, added from scratch), **WhatsApp Orders** (`customer_name`/`customer_phone`/`customer_address`, added from scratch), **Purchase Orders** (`po_number` only, added from scratch), **Inventory** (`product_code`/`name`/`sku`/`location_name` — this one's COUNT query already reused the same joined subquery as the main query, so all four were reachable). Reports and Activity Log were left as client-side (aggregate/grouped reports don't have a per-row `q` concept; Activity Log has no `q` precedent and joined/computed columns).

When wiring a new page: add `qField` state, include it in the list API call + `useEffect` deps, add a `searchByColumn(columnKey, value)` that does `setPage(1); setQField(columnKey); setQ(value);`, pass `onServerSearch={searchByColumn} serverColumn={qField} serverValue={q}` to `SearchByBar`, and make sure the page's separate top-level `SearchBox` (if it has one) resets `qField` to `""` before setting `q` — otherwise pressing that box stays narrowed to whichever column `SearchByBar` last had selected.

## Design system: Glass mode + Standard mode's 4 themes

Two independent toggles, both in `ProfilePage.jsx`'s Personalization card, both persisted per-browser (`ThemeContext.jsx`/`ModeContext.jsx`, localStorage): **Mode** (`data-mode`, "glass" default or "standard") and **Theme** (`data-theme`, "system"/"light"/"dark", plus a 4th "business" — see below). `theme.css` is the single source for every token both read from; no component hardcodes a color.

**"Business" theme** (new, Standard-mode-only): a 4th `data-theme` value modeled on a reference screenshot — white sidebar (no colored tint), one indigo/blue accent (`--bp-standard-accent: #4f6bed`) for primary buttons/active-nav/links, fully rounded pill-shaped status badges (`:root[data-mode="standard"][data-theme="business"] .bp-badge { border-radius: 999px }`), light gray-blue page background. It's deliberately **Standard-mode-only** — Glass mode has no styling for it at all, so `theme.css`'s dark-detection selector (`:not([data-theme="light"])`) explicitly also excludes `[data-theme="business"]`, and a bare `:root[data-theme="business"] { color-scheme: light; }` rule makes it fall back to looking like Glass Light if ever reached in Glass mode (reachable in principle, e.g. stale localStorage from switching modes, but not a real supported combination). `ProfilePage.jsx` only renders the "Business" swatch in the Theme picker while Mode=Standard is selected, and `PersonalizationCard`'s local `setMode` wrapper auto-reverts the stored theme to `"system"` the moment Mode leaves Standard while "business" was selected — so the picker never shows a chosen theme that's silently doing nothing.
